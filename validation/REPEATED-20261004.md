## Questions and scope

The repeated study tests whether the pilot's observed differences persist across more independent processes: retained instrumentation memory versus active sampling; shared versus independent caches; pressure policy versus a smaller cache; and individual request stalls around Compact. Repeated profiles examine whether cache-contention and Arena allocation paths recur across runs. The library implementation and worker binary are unchanged from the diagnostic pilot; this is measurement work, not a claim of an upstream optimization.

The frozen protocol ran **732 fresh worker processes**: **600 unprofiled jobs** with ten repetitions per condition and **132 profiled jobs** with six repetitions per condition. Suites and worker processes run sequentially. Expensive analysis runs only after measurements complete. The [repeated-study driver](../scripts/run-repeated-study.sh) applies the operation budgets and repetition counts below to the example configurations.

## Controls and measurement boundaries

Calibration uses the same cache workload across all five arms: no retained runtime-sample buffer or active timing; retained buffer only; retained buffer plus runtime sampling; retained buffer plus request timing; and retained buffer plus both. Four arms retain the same buffer capacity before baseline GC. The both-enabled condition also provides an ordinary shared-cache baseline, avoiding a duplicate baseline suite. Six million operations are a fixed budget, not a guarantee of five seconds per run; actual durations and sample coverage must accompany the results.

Topology holds GOMAXPROCS at four and changes request workers or sharing. Independent mode gives each worker its own 100,000-entry cache, so total capacity and live memory grow with worker count. Shared mode keeps one 100,000-entry cache. The harness control uses no real cache, retains only the latest payload per worker and emits no real-cache utility metrics. Its larger request budget makes its scaling diagnostic distinct from a matched absolute-throughput comparison with real caches.

Pressure conditions fix the request key space at 400,000, values at 256 bytes and the Go soft limit at 64 MiB. The three arms are capacity 200,000 with pressure reclamation off/on and capacity 100,000 with reclamation off. Observer-off repetitions provide the primary performance measurements. Otherwise matched observer-on repetitions record retention and pressure counters, with the observer's possible locking cost evaluated separately. Their periodic runtime-buffer settings remain matched. Final entry counts do not guarantee identical retention histories or hit/miss composition; successful-read throughput is calculated per run alongside total throughput.

Dense Compact fills 100,000 entries, deletes 75%, then runs two read-only request workers. The matched enabled/disabled arms keep 25,000 entries and record all 400,000 requests. Both retain the same request-trace capacity, allocated before the request phase but after baseline GC. The trace changes timing and live-memory costs relative to sparse sampling. Fixed trigger windows and actual-call overlap selections answer different questions; a brief interval with many short overlapping calls does not turn a few blocked calls into a stable population-tail estimate.

Profiles run in separate worker processes and are excluded from unprofiled performance rankings. CPU's longer operation budget improves sampling coverage; its profile totals are not directly comparable with the shorter mutex/block request totals. Allocation profiles use phase-boundary collections to publish delayed allocation data outside the workload timer. Profile-boundary allocations remain visible in allocation stacks and must be distinguished from workload sites. Per-operation attribution and repeat distributions are reported by profile kind and phase, without adding nested cumulative percentages.

## Comparison protocol and statistical limits

Comparisons pair the same repetition index and seed across the relevant conditions. Matching is validated using provenance, environment settings and deterministic workload accounting before calculating effects. Same-seed pairing is not a claim that every treatment executed immediately beside its control: the recorded execution schedule defines order and exposure to host drift.

Backend and sharing comparisons at the same request-worker count can use matching input checksums. Changing worker count changes the per-worker deterministic streams, and changing the harness control's operation budget changes its trace. Those comparisons retain the same workload policy but must not be described as identical request traces or bypass a checksum mismatch silently.

The effect summary uses paired log ratios and an order-statistic interval for their median. With ten independent, exchangeable pairs, the selected symmetric order-statistic interval has approximately **97.85% coverage** under the continuous common-distribution model. Ratios exponentiate those bounds; the estimator is a median of paired effects, not a ratio of separately reported group medians. Repetition seeds vary, so inference covers the recorded seed policy and execution conditions rather than a universally fixed request trace.

Exploratory paired sign tests receive Holm adjustment within declared category/metric families and across all 546 comparisons. The analysis estimated 534 comparisons; 12 non-estimable Compact comparisons remained in the family with p=1: six GC ratios had zero costs and six Map/Arena trigger-window ratios had clipped windows. Exact zero differences are handled and reported separately from nonzero signs. The small number of pairs, tied or discrete outcomes, multiple selected metrics, host drift and observation overhead constrain interpretation. Adjusted p-values and interval bounds are evidence for the specified comparison, not automatic backend-winner labels or proof of a particular causal mechanism. Zero or otherwise invalid ratio denominators must be reported rather than converted into finite log ratios.

With ten pairs, the smallest possible two-sided exact sign-test p-value is 0.001953125. The first global Holm threshold for 546 comparisons is approximately 0.0000916, so no comparison could pass global 5% rejection even if all ten signs agreed. All global adjusted p-values were 1. This is a planned-design power limit, **not evidence of equal performance or no effect**. Individual 97.85% intervals are not simultaneous intervals over the whole matrix; the smaller-family results remain exploratory.

Profile repeats receive separate descriptive attribution summaries. Allocation-profile ranges below are the minimum and maximum across six independent processes, not confidence intervals. Sampled contention delay sums waiting across goroutines; it is not request wall time. CPU profiles describe sampled execution, allocation profiles estimate bytes at sampled allocation sites, and block profiles include runner/channel waits. The consistency of a hotspot across six runs supports a narrower investigation than attributing the entire throughput difference to that site.

## Findings

The following tables use medians of ten unprofiled processes per condition. Paired ratios are computed separately from each matched seed/repetition and must not be reconstructed by dividing table medians. The [comparison analyzer](../scripts/analyze-repeated.py) implements the paired estimators and integrity checks.

### Baseline throughput and GC remain different evaluation axes

The calibration arm with both runtime and request sampling enabled uses 100,000 entries, 256-byte values, 90% reads, one request worker, GOMAXPROCS two and no runtime memory limit:

| Backend | Million operations/s | Allocated B/op | GC CPU ns/op |
|---|---:|---:|---:|
| Map | 3.524 | 81.520 | 53.036 |
| Radix | 1.432 | 83.009 | 60.733 |
| Arena | 2.989 | 76.986 | 13.715 |

For Arena relative to Map, the paired throughput ratio was **0.859**, with an individual 97.85% median-ratio interval of **[0.761, 0.917]**. Its paired GC CPU/op ratio was **0.268 [0.212, 0.286]**, and allocation ratio **0.9445 [0.9444, 0.9450]**. The repeated observations support lower Arena GC CPU cost alongside lower mixed-workload throughput in these conditions; GC CPU is not wall-clock request time. These individual intervals do not override the global multiplicity limitation above.

The five-arm calibration now holds buffer retention fixed when comparing active instrumentation. Both-enabled versus buffer-only paired throughput ratios were Map **0.877 [0.824, 1.029]**, Radix **0.923 [0.821, 1.171]** and Arena **0.981 [0.919, 1.116]**. Each interval includes one, so these data do not support a precise universal overhead percentage or zero-overhead claim. Median measured durations in the both-enabled arm were 1.70, 4.19 and 2.01 seconds for Map, Radix and Arena respectively; the fixed six-million-request budget did not give every backend five seconds of measurement.

### Independent caches and repeated profiles identify sharing costs

At four request workers and GOMAXPROCS four:

| Backend | Shared Mops/s | Independent Mops/s | Paired independent/shared ratio | Individual 97.85% interval |
|---|---:|---:|---:|---|
| Map | 0.850 | 7.250 | 7.965 | [7.747, 9.117] |
| Radix | 0.377 | 3.170 | 8.311 | [7.767, 8.505] |
| Arena | 0.681 | 6.557 | 9.460 | [7.945, 10.010] |

Independent caches retained 400,000 total entries; shared caches retained 100,000. This is a sharing control with different total live state, not a fourfold-capacity-normalized comparison. The synthetic harness scaled from 4.260 Mops/s with one worker to 19.101 and 25.146 with four/eight workers, using its separate 16-million-request budget. It does not measure real cache utility, and its four/eight-worker phase medians remained below one second.

Across all six shared-cache mutex profiles per backend, cache-unlock stacks accounted for approximately 100% of sampled mutex delay. Median sampled delay attributed to those stacks was **1,707.95 ns/op for Map, 7,969.79 for Radix and 3,209.38 for Arena**. No samples were attributed to the same cache-unlock site in the corresponding independent-cache profiles. CPU profiles also repeatedly attributed substantial shared-mode work to `RWMutex.Lock`: median 28.18%, 13.17% and 18.85% for Map, Radix and Arena, compared with 2.86%, 1.03% and 2.17% in independent mode. This locates recurring contention paths without attributing every throughput difference to one lock. Profile percentages summarize each run’s attributed samples as a fraction of that run’s sampled total. The [profile analyzer](../scripts/analyze-profile-repeats.py) normalizes sampled costs per operation before summarizing repetitions.

### Pressure savings have cache-utility and allocation costs

These primary pressure results have the periodic cache observer disabled. Every condition uses the same 400,000-key space and 64 MiB soft limit:

| Backend / condition | Mops/s | Million read hits/s | Allocated B/op |
|---|---:|---:|---:|
| Map 200k, pressure off | 0.801 | 0.360 | 83.392 |
| Map 200k, pressure on | 0.933 | 0.210 | 103.280 |
| Map 100k, pressure off | 0.971 | 0.218 | 85.572 |
| Radix 200k, pressure off | 0.554 | 0.249 | 82.388 |
| Radix 200k, pressure on | 0.865 | 0.198 | 94.236 |
| Radix 100k, pressure off | 1.237 | 0.278 | 87.737 |
| Arena 200k, pressure off | 0.831 | 0.374 | 78.123 |
| Arena 200k, pressure on | 0.968 | 0.222 | 143.361 |
| Arena 100k, pressure off | 1.835 | 0.413 | 78.747 |

Read-hit throughput is calculated exactly per run before aggregation. The large pressure-off arms had approximately 50% hits; dynamic-on and small-off arms approximately 25%. The descriptive group medians of total throughput were higher with reclamation, while group-median successful-read throughput was lower than in the large pressure-off caches. This is not the paired effect estimate: Map's paired on/off throughput ratio was 0.958 despite its higher separate on-group median. The small off condition can differ again because it avoids dynamic shedding and rebuilding. These outcomes cannot be converted into service-level benefit without including the cost of misses.

Arena's observer-off on condition retained a median 102,809.5 entries and recorded nine tier-2 compactions, compared with zero compactions in both off controls. Its allocation increase persisted despite the small-off control's similar retention. In six separate allocation-profile repeats, pressure-on runtime allocation was **149.56 B/op [143.51, 149.84]**, versus approximately 78 B/op in both off controls. `compactDataStructuresLocked` and `allocateNode` appeared in all six on profiles, with median flat attribution **32.11 and 30.94 sampled B/op** respectively; neither site received allocation samples in either off control. One-million-entry fill separately attributed **490.32 sampled B/op**, about 54.95% of sampled bytes, to node growth across six profiles. These repeatable paths narrow the growth/rebuild investigation; they do not demonstrate the benefit of an unimplemented optimization.

Observer-on suites ran after observer-off suites, with identical seed matching but no temporal interleaving between those suites. Throughput differences varied in direction and magnitude. For example, Map's large pressure-off observer ratio was **1.146 [0.976, 1.756]**, while the small-off ratios were Radix **0.644 [0.569, 0.739]** and Arena **0.750 [0.665, 0.850]**. Stats locking, GC behavior and time-dependent host effects cannot be separated completely by this schedule. Use observer-off results as the primary performance data and observer-on traces to study retention, rather than interpreting all differences as observer CPU overhead.

### Dense traces repeatedly capture requests overlapping Compact

All 60 enabled/disabled jobs retained 25,000 entries through the probe and captured every one of their 400,000 requests without trace drops: **24 million observations** overall. Each backend has ten actual Compact events:

| Backend | Compact duration median [min, max], ms | Events with an overlapping call longer than 1 ms |
|---|---:|---:|
| Map | 4.129 [2.182, 6.547] | 10/10 |
| Radix | 0.075959 [0.003662, 0.316061] | 0/10 |
| Arena | 8.146 [5.266, 16.220] | 10/10 |

Every Map event had two overlapping calls longer than 1 ms. Arena had two in nine events and one in the remaining event. Complete tracing therefore reproduced individual stalls missed by the sparse pilot. The event interval includes scheduling and lock acquisition, so overlap is not an isolated lock-holding-time measurement. Eighteen fixed windows across fourteen jobs were clipped by short phase boundaries; affected full-ten-pair window comparisons were withheld rather than silently using fewer pairs. These calls and events do not establish an open-loop service p99, and whole-phase enabled/disabled throughput must not be treated as the duration of the Compact stall.
