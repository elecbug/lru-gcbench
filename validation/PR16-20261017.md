# PR #16 verification — 2026-10-17

The existing strict/race suites and `go vet` passed for both modules of [google/go-lru PR #16](https://github.com/google/go-lru/pull/16). Additional tests reproduced an unresolved descendant-goroutine reentrancy problem in all three backends. A focused performance comparison also exceeded the project's relative regression budget for two Map callback/Replace cases.

The C-03 reentrancy remediation needs another correction before it can be considered complete.

## P1: descendant detection stops after eight live ancestors

The ancestor search in [pressure.go](https://github.com/google/go-lru/blob/3cfeab260c416741b3c66509843eab5983cf5fd6/pressure.go#L319-L361) has a hard limit of eight hops. On reaching that limit, it returns the same negative result used for an unrelated goroutine.

An eviction callback can spawn a chain of goroutines, wait for that chain to finish, and have the deepest child delete a second key from the same cache. Every ancestor stays alive waiting for its child, so this reproduction does not depend on missing or exited parents. With twelve hops, the callback holder is never reached. The deepest child's callback delivery then blocks on [evictCallbackMu.Lock](https://github.com/google/go-lru/blob/3cfeab260c416741b3c66509843eab5983cf5fd6/pressure.go#L1538-L1555), while the holder waits for that child. Neither call can finish.

The same limit affects [pressure sampling](https://github.com/google/go-lru/blob/3cfeab260c416741b3c66509843eab5983cf5fd6/pressure.go#L1143-L1169): a descendant Put invokes the custom pressure function again instead of taking the reentrant bypass. The test arms the outer hook only once to bound execution and observes two hook invocations where one is expected. A hook that always waits for another such descendant can recurse repeatedly.

| Descendant depth | Map | Radix | Arena |
|---|---|---|---|
| 1 | Both checks pass | Both checks pass | Both checks pass |
| 8 | Both checks pass | Both checks pass | Both checks pass |
| 12 | Callback blocks; pressure hook called twice | Callback blocks; pressure hook called twice | Callback blocks; pressure hook called twice |

All eighteen check instances ran with the race detector. The twelve shallow instances passed and the six depth-twelve instances failed. No data race was reported; the failures concern liveness and hook invocation semantics. An overlay control changing only `maxAncestorHops` from 8 to 64 passed both additional scenarios on every backend, confirming the depth limit as the cause. Raising a fixed limit only moves this boundary. Exhaustion of a heuristic ancestry search must not silently authorize a blocking callback-lock acquisition.

This is a residual C-03 boundary case in the PR's intended remediation. The base already contains the broader callback-reentrancy defect.

## P2: callback Replace exceeds the relative performance budget

The focused rerun pinned both versions to CPU 31, used `GOMAXPROCS=1`, 500 ms per benchmark and six independent test processes per version. Base/head order alternated A/B then B/A across repetitions. Values below are medians; bracketed values are observed minimum/maximum ranges, not confidence intervals.

| Operation | Base ns/op [min, max] | PR ns/op [min, max] | Median change |
|---|---:|---:|---:|
| Map Get, nested depth 2 | 35.790 [35.08, 37.88] | 34.665 [33.62, 37.23] | -3.1% |
| Map Replace with value callback | 54.580 [50.14, 68.20] | 86.345 [82.51, 90.18] | +58.2% |
| Map Replace with entry callback | 53.675 [51.39, 65.21] | 90.250 [85.20, 92.88] | +68.1% |

The PR's `benchcheck` reported two relative regressions with `-check-targets=false -strict-missing`: both callback cases exceeded the default 35% ns/op increase threshold and the minimum absolute-delta requirement. All three rows reported 0 B/op and 0 allocs/op in both versions.

The affected path now includes [serialized callback delivery](https://github.com/google/go-lru/blob/3cfeab260c416741b3c66509843eab5983cf5fd6/pressure.go#L1841-L1863), tag ownership and queue dispatch. This supports reviewing the additional work and making an explicit performance-budget decision for callback safety. It does not assign an exact share of the measured cost to each instruction.

## Custom pressure sampling improves substantially

The same pinned protocol included a small public-API benchmark: construct a 10,000-entry cache with `WithPressureFunc(func() float64 { return 0.1 })`, insert the fixed key `hot` before timing, and repeatedly update that key. The benchmark body was identical in base and head.

| Backend | Base ns/op [min, max] | PR ns/op [min, max] | Ratio of medians, base/PR |
|---|---:|---:|---:|
| Map | 6060.5 [5542, 7252] | 143.85 [140.4, 145.7] | 42.1× |
| Radix | 6302.5 [5527, 7149] | 144.70 [138.7, 148.1] | 43.6× |
| Arena | 5996.0 [5616, 7336] | 149.65 [143.7, 153.3] | 40.1× |

Both versions reported 0 B/op and 0 allocs/op for these cases. This supports the pressure-sampling improvement on this machine; it does not establish the same speedup for mixed traffic, contention or reclamation.

## Reproduce the additional correctness checks

First create a detached worktree at the head SHA above. Then, from this benchmark repository, run:

```sh
./scripts/check-hook-reentrancy.sh /path/to/pr16-checkout /tmp/pr16-hook-check
```

The [reproduction script](../scripts/check-hook-reentrancy.sh) adds its external tests through a Go overlay, executes depths 1, 8 and 12 independently for each backend, and returns nonzero if any scenario fails. It records its invocation commands and diagnostics. A new output path is required for each attempt. The depth-twelve failures are expected for the pinned PR head.

The native callback and Get benchmarks are defined in the PR's [benchmark source](https://github.com/google/go-lru/blob/3cfeab260c416741b3c66509843eab5983cf5fd6/benchmarks_test.go). The additional pressure benchmark uses this body with each backend constructor:

```go
cache := constructor(10000, lru.WithPressureFunc(func() float64 { return 0.1 }))
_, _ = cache.Put("hot", 1)
b.ReportAllocs()
b.ResetTimer()
for b.Loop() {
    _, _ = cache.Put("hot", 1)
}
```

Keep the code, toolchain, operation and key policy identical between versions. Use the same CPU selection and alternating process order when repeating the focused comparison.
